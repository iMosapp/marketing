# P0 security investigation: super-admin credentials in Company Docs (Oct 13 2026) — READ-ONLY report, no changes made

## Confirmed findings
1. **`memory/PRD.md` (tracked, in GitHub) contains credential literals**: line 404 "Admin login: <preview super-admin email> / <password>", lines 21, 26, 27, 29 four QA-account email/password pairs (`@invalid.imonsocial.test`, preview-only orgs). First committed 2026-02-22 (commit 9880ef295); present in 8 PRD.md revisions. Also a historical **MongoDB Atlas connection string WITH password** (user `im…n`, 20-char password, cluster `…tuuucd.mongodb.net`) in PRD.md at commits d4005cf50 / 782935b7d (2026-02-26), removed afterwards but still in Git history. The current PRD.md has no connection string and no API keys (the only `sk_test_…` hit is a 16-char placeholder, not a key).
2. **The PRD is published to Company Docs on every deploy** (`backend/routers/docs.py` `REPO_DOC_SOURCES` -> slug `imos-prd-working-log`, "PRD Working Log (Full Build History)", `sync_repo_docs()` run from `server.py` startup `_doc_sync`, since commit 65773abd8 of 2026-08-20). The stored copy is 693,188 chars, `is_published: true`, **no `required_role`**. Preview DB verified: the stored document contains the super-admin password marker, a QA password marker and the string `mongodb+srv://` (the latter only as a mention, no URL). Production runs the identical code and file, so the same document exists in production `company_docs` (deployed Oct 11 and Oct 13); not readable from here without production credentials.
3. **Who can read it today** (live probes against the preview API, same code as production): anonymous -> 401; regular rep (`role user`) -> 403; **store_manager -> 200 (listed + full content)**; **org_admin -> 200 (listed + full content)**; super_admin -> 200. `company_docs` is a global collection with **no tenant scoping**, so a store manager or org admin of ANY customer organization can read it. Routes: `GET /api/docs/` (list; `search` matches title/summary only), `GET /api/docs/{doc_id}` (full content), `GET /api/docs/prd` (curated PRD slug, no secrets; its auto-seed fallback still reads `/app/memory/PRD.md` if the slug is missing). `GET /api/docs/{id}/export-pdf` and `POST /api/docs/{id}/email-pdf` are super-admin-only (403 for managers, verified). `X-User-ID` spoofing is blocked by the identity middleware (401 without a matching Bearer token, verified).
4. **AI retrieval**: `services/leadership/knowledge.doc_passages()` keyword-scans ALL published Company Docs (working log included) and injects up to 4 paragraphs into Leadership Team / Strategic Advisor prompts (`services/leadership/ask.py:66`, `orchestrator.py:283` use the default `include_docs=True`). Reachable only through `/api/command-center/*`, gated by `require_cc` (owner-tool visibility, owner / explicitly granted super admins). Not an exposure to managers, but secrets can reach the LLM prompt.
5. **Other tracked files with credential literals**: `TEST_DATA_TRACKER.md` (37 synthetic `@sunshineauto.test` accounts with temp passwords, Feb 2026; none exist in preview; production unknown), `MVP_SUMMARY.md` (curl example with a dummy password), `backend/seed_demo_data.py`, ~188 `backend/tests/*.py` using the preview super-admin and QA passwords literally (known since the Sep 30 hygiene scan, rotation "step 7" never done).
6. **Session model**: JWTs are 30-day, signed with `JWT_SECRET`, carry `iat`, and there is NO password-change or revocation check in `verify_jwt_token` -> changing a password does not invalidate tokens already issued. Only `access_block` (full block of a user) or rotating `JWT_SECRET` (logs everyone out) invalidates sessions today. `JWT_SECRET` was never committed (the only committed `backend/.env`, Feb 21 2026, held MONGO_URL=localhost, DB_NAME, CORS, and a Resend key that differs from the current one).
7. **No access logging** of Company Docs reads exists (no API request log collection; pod logs only record identity rejections). There is therefore no evidence of unauthorized access and no way to prove its absence: the exposure is POTENTIAL, open to every production org_admin / store_manager account since the first production deploy after 2026-08-20.

## Session invalidation without rotating JWT_SECRET + a second P0 found and fixed (Oct 13 2026, preview only, NOT deployed)
### New finding (CRITICAL, fixed in the same change)
`GET /api/auth/me` trusted the `imonsocial_session` cookie, whose value was the user's bare ObjectId, and answered with the user record **and a fresh 30-day JWT**. User ids are not secret (they travel as `X-User-ID` on every request, in URLs and in admin lists). Verified live in preview before the fix: a request with `Cookie: imonsocial_session=<super admin id>` and no token returned 200 with a `super_admin` JWT. Consequences: (1) a password-less login for ANY account by anyone who knows its id; (2) the planned session cutoff would have been useless (one request mints a fresh, post-cutoff token). Exposure window: since the cookie restore was introduced (session cookies are set by `/auth/login`, `/auth/me`, `/auth/refresh`, `/auth/activate/complete`); no access log exists, so treat as potential exposure, same as the Company Docs finding.

### Code (all in preview, HEAD after this step; parent `616ecddbb`)
- `routers/auth.py`: `sessions_valid_after()` parses `SESSIONS_VALID_AFTER` (ISO-8601 UTC such as `2026-10-14T15:30:00Z`, also `+00:00` / naive / space-separated forms, or Unix epoch seconds; unset or blank = no cutoff); `issued_after_cutoff(payload)` rejects a token whose `iat` is missing, non-numeric or earlier than the cutoff, and FAILS CLOSED (every session rejected + one ERROR log line per request "SESSIONS_VALID_AFTER is malformed") when the value cannot be parsed. Applied in `verify_jwt_token` (used by the identity middleware, `rbac.get_current_user`, the websocket and every router that decodes tokens) and in `/auth/refresh` (the Face ID path decodes with `verify_exp=False`; without the gate an old token could be traded for a fresh one). Signature, expiry and the future-`iat` rejection of PyJWT are unchanged. `GET /auth/me` now accepts only a valid signed JWT (Bearer header or the httponly cookie), checks the account is active and not blocked, and returns a fresh session; a bare id, a forged token, an expired token or a `mock_token_` -> 401. `set_session_cookies()` (one helper for login / me / refresh / activation) stores the JWT itself in the httponly cookie, max-age 30 days (was the bare id for 10 years).
- `routers/rbac.py resolve_impersonation_session`: an `impersonate_*` session row created before the cutoff is dead too (they are 8 h DB rows; without this they would have outlived the cutoff by up to 8 h).
- `seed_demo_data.py`: refuses to run against a non-local database unless `ALLOW_DEMO_SEED=1` (flagged by the readiness scan: the script hard-deletes the demo user's contacts/messages; it was never called at startup).
- `JWT_SECRET` untouched. No DB migration. No frontend change (the web client already treats a 401 from `/auth/me` as "sign in again").
