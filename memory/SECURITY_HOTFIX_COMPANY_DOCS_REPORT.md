# P0 security investigation: super-admin credentials in Company Docs (Oct 13 2026) — READ-ONLY report, no changes made

## Confirmed findings
1. **`memory/PRD.md` (tracked, in GitHub) contains credential literals**: line 404 "Admin login: <preview super-admin email> / <password>", lines 21, 26, 27, 29 four QA-account email/password pairs (`@invalid.imonsocial.test`, preview-only orgs). First committed 2026-02-22 (commit 9880ef295); present in 8 PRD.md revisions. Also a historical **MongoDB Atlas connection string WITH password** (user `im…n`, 20-char password, cluster `…tuuucd.mongodb.net`) in PRD.md at commits d4005cf50 / 782935b7d (2026-02-26), removed afterwards but still in Git history. The current PRD.md has no connection string and no API keys (the only `sk_test_…` hit is a 16-char placeholder, not a key).
2. **The PRD is published to Company Docs on every deploy** (`backend/routers/docs.py` `REPO_DOC_SOURCES` -> slug `imos-prd-working-log`, "PRD Working Log (Full Build History)", `sync_repo_docs()` run from `server.py` startup `_doc_sync`, since commit 65773abd8 of 2026-08-20). The stored copy is 693,188 chars, `is_published: true`, **no `required_role`**. Preview DB verified: the stored document contains the super-admin password marker, a QA password marker and the string `mongodb+srv://` (the latter only as a mention, no URL). Production runs the identical code and file, so the same document exists in production `company_docs` (deployed Oct 11 and Oct 13); not readable from here without production credentials.
3. **Who can read it today** (live probes against the preview API, same code as production): anonymous -> 401; regular rep (`role user`) -> 403; **store_manager -> 200 (listed + full content)**; **org_admin -> 200 (listed + full content)**; super_admin -> 200. `company_docs` is a global collection with **no tenant scoping**, so a store manager or org admin of ANY customer organization can read it. Routes: `GET /api/docs/` (list; `search` matches title/summary only), `GET /api/docs/{doc_id}` (full content), `GET /api/docs/prd` (curated PRD slug, no secrets; its auto-seed fallback still reads `/app/memory/PRD.md` if the slug is missing). `GET /api/docs/{id}/export-pdf` and `POST /api/docs/{id}/email-pdf` are super-admin-only (403 for managers, verified). `X-User-ID` spoofing is blocked by the identity middleware (401 without a matching Bearer token, verified).
4. **AI retrieval**: `services/leadership/knowledge.doc_passages()` keyword-scans ALL published Company Docs (working log included) and injects up to 4 paragraphs into Leadership Team / Strategic Advisor prompts (`services/leadership/ask.py:66`, `orchestrator.py:283` use the default `include_docs=True`). Reachable only through `/api/command-center/*`, gated by `require_cc` (owner-tool visibility, owner / explicitly granted super admins). Not an exposure to managers, but secrets can reach the LLM prompt.
5. **Other tracked files with credential literals**: `TEST_DATA_TRACKER.md` (37 synthetic `@sunshineauto.test` accounts with temp passwords, Feb 2026; none exist in preview; production unknown), `MVP_SUMMARY.md` (curl example with a dummy password), `backend/seed_demo_data.py`, ~188 `backend/tests/*.py` using the preview super-admin and QA passwords literally (known since the Sep 30 hygiene scan, rotation "step 7" never done).
6. **Session model**: JWTs are 30-day, signed with `JWT_SECRET`, carry `iat`, and there is NO password-change or revocation check in `verify_jwt_token` -> changing a password does not invalidate tokens already issued. Only `access_block` (full block of a user) or rotating `JWT_SECRET` (logs everyone out) invalidates sessions today. `JWT_SECRET` was never committed (the only committed `backend/.env`, Feb 21 2026, held MONGO_URL=localhost, DB_NAME, CORS, and a Resend key that differs from the current one).
7. **No access logging** of Company Docs reads exists (no API request log collection; pod logs only record identity rejections). There is therefore no evidence of unauthorized access and no way to prove its absence: the exposure is POTENTIAL, open to every production org_admin / store_manager account since the first production deploy after 2026-08-20.

## Minimum remediation (Phase B proposal, awaiting approval)
Code (`backend/routers/docs.py`, ~25 lines; `services/leadership/knowledge.py`, 1 line):
1. `REPO_DOC_SOURCES`: `"required_role": "super_admin"` on `imos-prd-working-log` (recommended also on `imos-operations-manual`, `imos-app-scope`, `imos-tech-stack`, `product-requirements-document`: internal engineering docs; integrations docs are public anyway; legal/policy/training docs keep manager access). `list_docs` and `get_doc` already enforce `required_role`.
2. `sync_repo_docs`: a publish gate that refuses (skips + logs) any repo doc whose content matches a credential pattern (email/password pair, `mongodb+srv://…@`, `sk-`/`rk_`/`sk_live`/`whsec_`/`re_` tokens), so a future PRD can never republish secrets. Same gate applied when the stored copy is rewritten.
3. `GET /docs/prd` auto-seed fallback: read `/app/docs/PRODUCT_REQUIREMENTS.md` instead of `/app/memory/PRD.md`.
4. `knowledge.doc_passages`: skip docs with `required_role == "super_admin"` (keeps secrets out of LLM prompts; the owner still has the curated docs).
5. Session invalidation hook (optional, 6 lines): `users.tokens_valid_after` checked in `verify_jwt_token` (`iat` older -> reject) so a password change can log out one account without rotating `JWT_SECRET`.
Data:
6. Sanitize `memory/PRD.md` (5 lines: replace the email/password literals with "see test_credentials.md (not in repo)"), `TEST_DATA_TRACKER.md` (password column -> "rotated"), `MVP_SUMMARY.md` (placeholder), `seed_demo_data.py` (env/generated passwords). The sync is hash-based: on the next backend start/deploy the sanitized PRD overwrites `imos-prd-working-log` in preview and production (no manual DB edit needed; nothing else in `company_docs` is touched). Backup: `mongoexport` of the one document before the deploy (or rely on Git: the doc is fully regenerated from the repo file). Rollback: previous checkpoint + redeploy republishes the old text, so rollback must not be used for this change.
7. Tests: one shared `backend/tests/qa_creds.py` reading credentials from a gitignored `backend/tests/.qa_credentials.json` (fallback env vars), and a scripted replacement of the literal passwords in the ~188 test files with `qa_creds.X` — mechanical, required BEFORE the preview password rotation or every suite breaks.
Rotation (owner-controlled, nothing automated):
8. Production: Admin > Users: check for a `…@imosapp.com` super admin; if present change its password or disable it. Change the production owner password if it was ever the same. Then rotate `JWT_SECRET` in Deployment Secrets + Deploy (invalidates every session; all users log in again) — or approve item 5 and use it for the affected account only. Preview: rotate the preview super-admin password (owner or approved script), update `memory/test_credentials.md` + `.qa_credentials.json`.
9. Ask Emergent support to confirm the production Mongo credential was rotated after 2026-02-26 (or approve the read-only equality check); confirm the Feb 2026 Resend key is revoked in the Resend dashboard.
10. Review: production Admin > Users for org_admin / store_manager accounts outside your organization (these are the only roles that could read the document) and their last-login dates; pod logs for `[IDENTITY] Rejected` lines. Optional 5-line change: log every `GET /api/docs/{id}` read (user, role, slug) so this is auditable from now on.
11. Git history: 8 PRD revisions + 188 test files + the Feb 2026 Atlas URL / Resend key. Rotation makes the history harmless; rewriting a shared repository is disruptive and not recommended unless the repo is public. Decision for the owner.
Regression tests (`tests/test_company_docs_access.py`): super admin lists + reads the working log (200); store_manager and org_admin: not listed, GET by id 403, export 403, `/docs/prd` 403 if restricted, search returns nothing restricted; rep 403; anonymous 401; `X-User-ID` without token 401; `doc_passages` never returns a restricted paragraph for a question that matches the working log; the sync gate skips a temp file containing a credential pattern; every published doc in preview is free of credential patterns; integrations/legal docs remain readable by managers (tenant isolation: the QA org admin and the QA manager belong to two different orgs).
Deploy: Save to GitHub -> Deploy -> owner verifies as super admin (working log still present, content sanitized) and as a manager account (not listed, 403 by id) -> anonymous probes. The new build and the Secrets rotation can ship together.

GO for the remediation above, in this order: (1) code + PRD sanitisation + tests in preview (same day), (2) owner rotates passwords and `JWT_SECRET`, (3) Deploy, (4) verify.
