# RCA — Live Jessi (GPT-Live / WebRTC): session created (HTTP 200 + SDP answer) but `session.started` never delivered

**Deployment:** imos-deploy-prep (`b1e5ea0d…`) · **Active run:** `1d660baa` (redeploy, SUCCESS, promoted 2026-10-06T23:11:54Z)
**Reporter:** owner `69be2bc65c4c5af1e821aecc` (Forest Ward) · iPhone live sheet: "Connecting to Jessi · gleam", spinner, 0:00, never speaks, ends.

## TL;DR
The backend creates the OpenAI live session successfully — every `POST /api/live-voice/session` returned **HTTP 200** with a valid SDP answer and an `openai_session_id` was stored. The phone applies the answer but **never receives the `session.started` event on the `oai-events` data channel**, so audio never starts (`seconds=0`, empty transcript), and the user ends the sheet.

**This is NOT caused by the afternoon deploys.** The entire live-session code path (backend `create_session` + the OpenAI request payload + `routers/live_voice.py` + all frontend WebRTC hooks) is **byte-identical** to the build that was serving a *working* session at 23:03Z, 8 minutes before the suspect deploy promoted. The only code delta in run `1d660baa` is one cosmetic field in `serialize()` that never runs on the live path. The fault is **external to the app — on the OpenAI GPT-Live (`gpt-live-1`) realtime side** (or the phone↔OpenAI media path).

## Root cause
The OpenAI GPT-Live session is established at the HTTP/SDP layer (200 + SDP answer + `openai_session_id`) but the realtime session **never initializes on the data channel** (`session.started` never arrives, and no `error` event is sent either). Because the backend request payload and the entire phone-side WebRTC/data-channel code are byte-identical to a build that worked at 23:03Z, and our backend/pods/secrets are healthy, the failure lies **outside the app** — on OpenAI's `gpt-live-1` realtime service (service incident, project/account access to `gpt-live-1` realtime, or a realtime/concurrency quota), or the phone↔OpenAI media path. The timing overlap with the 23:11 deploy is **coincidental** — that deploy changed no code on the live path.

Note: important detail — `session.started` travels directly **phone ↔ OpenAI** over WebRTC; our backend only brokers the SDP once over HTTP. So even a backend/pod networking issue could not explain a missing `session.started` after a successful SDP broker. This further isolates the fault to OpenAI (or the client network).

## What could NOT be reproduced here
A live WebRTC session needs the real `OPENAI_API_KEY` and a phone↔OpenAI media path; the sandbox has neither, and OpenAI's service status is not visible from this tooling. The external cause is reached by **elimination** (every app-side component on the path is unchanged and healthy), not by direct reproduction — the positive confirmation (OpenAI incident/quota) must be checked on OpenAI's side.
