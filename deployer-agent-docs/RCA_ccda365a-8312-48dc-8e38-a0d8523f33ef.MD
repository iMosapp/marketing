## Verdict (one line)
zzdlg did NOT crash from the clean-up tasks throwing. It was killed 3× by the **container entrypoint's own readiness gate** — `Backend failed to start within timeout, exiting` (PID-1 exit 1) after `attempt 60/60` — because the backend's cold start (heavy import ~45–60s + the in-lifespan startup clean-up tasks ~10s, which run on BOTH replicas concurrently with no cross-replica lock) exceeded the entrypoint's ~60-attempt (~60s) budget. m4d99 won the startup race (~61s) and stayed up; zzdlg lost under the concurrent-startup DB contention and crash-looped until the contention cleared, then came up cleanly at 02:05. NOT an OOM.

## 5. SCHEDULER ON BOTH REPLICAS — CONFIRMED
Both replicas start their own APScheduler: `Campaign scheduler started` + `[Scheduler] Started with 56 jobs` logged once per replica (m4d99 01:32:19, zzdlg 02:05:09) = **2 independent schedulers, no leader election**. The 5-minute tick logs use per-worker IDs (`worker sched-xxxxxxxx`) and an atomic claim (`Atomically claimed 0 sends`), so sends are de-duplicated at the DB layer — but both replicas DO run the loop, and both run the full startup clean-up. This is the same no-cross-replica-lock pattern that drove the crash.

## ROOT CAUSE (proven)
The platform entrypoint runs `uvicorn server:app --port 8001`, then polls the backend up to **60 attempts (~60s)** and, on timeout, prints `Backend failed to start within timeout, exiting` and exits (container exit 1 → CrashLoopBackOff). The app's cold start is close to that budget: module import/app construction (CORS line at 02:04:20) to lifespan entry (02:05:03) ≈ **43s**, plus the in-`lifespan` startup clean-up (Quick shops, Twilio number, scheduler, voice/account backfills, phone consolidation) ≈ **10s**, and uvicorn only binds the port AFTER lifespan startup completes. The clean-up tasks run on **both replicas simultaneously with no cross-replica lock** (phone consolidation merged the same duplicate on both boots), so when both pods boot together (01:31:16) they contend on the same DB; m4d99 finished at ~61s (just inside the gate) and stayed up, while zzdlg slipped past 60s and was killed — repeating for 3 cycles (01:31:58 → ~02:01:55) until m4d99's startup load cleared, after which zzdlg completed in time (02:05) and has been healthy since.

## SUGGESTED FIXES
1. **Code (E1) — durable fix:** Move the startup clean-up/backfill tasks OUT of the blocking FastAPI `lifespan`/startup path so uvicorn binds `:8001` immediately (e.g. kick them off as background `asyncio` tasks after `yield`, or after the server is accepting). AND gate them behind a **cross-replica run-once lock / leader election** (reuse the existing `migrations` collection atomic-claim pattern) so only ONE replica runs the clean-up and the two pods stop contending on the same DB work on every boot. Same leader guard should ideally cover the APScheduler loop. This removes both the slow blocking startup and the concurrent-contention that pushed zzdlg over the gate.
2. **Platform (secondary):** The entrypoint's fixed ~60-attempt (~60s) backend-readiness timeout is marginal for this heavy image (healthy boot already takes ~61s). Raising that budget in the deploy template (entrypoint.sh) would give headroom, but the real fix is #1 — do not rely on the timeout bump alone.

No emergency: the app is live and both replicas are currently Ready; this was a transient, self-recovered boot-time crash-loop on one replica.
