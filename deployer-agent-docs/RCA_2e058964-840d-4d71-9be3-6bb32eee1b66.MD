# RCA — Owner (super_admin "Forest Ward") sees only 17 tools, owner-only entries missing

## Headline (answers your Q1)
**OWNER_EMAIL is PRESENT in the production backend environment and its value is exactly `forest@imosapp.com` (the expected value).**
- `list_secrets` on the active run (2e058964): `OWNER_EMAIL` → `is_empty: false`, `matches_expected: true` (compared against `forest@imosapp.com`).
- So the symptom is **NOT** a missing/blank/wrong OWNER_EMAIL env var.

## Actual root cause
**`OWNER_EMAIL` points at an email that no user account has.** `ensure_owner_flag()` reads `OWNER_EMAIL=forest@imosapp.com` and sets `is_owner:true` on the user whose email matches (case-insensitive). In production there is **no user with email `forest@imosapp.com`**, so it matches nobody and `is_owner` is never set → `GET /api/owner/visibility` returns `is_owner:false` → the owner-only menu entries are hidden → the owner sees the 17-tool non-owner view.

Evidence from the production DB (`imos-admin-test_database`):
- Users matching "forest" (2 found), both `role: super_admin`, name "Forest Ward":
  - `forest@imonsocial.com`  (the account the owner logs in with on his iPhone — imonsocial.com = the production app domain)
  - `merged_forest@imosapp.com`  (looks like the old `forest@imosapp.com` account after an email merge/rename)
- `count(email == "forest@imosapp.com")` → **0** (exact, case-insensitive). The email OWNER_EMAIL targets no longer exists.
- `count(is_owner == true)` → **0**. No user in the whole collection carries the owner flag.

Net: an email migration renamed the original `forest@imosapp.com` owner account to `merged_forest@imosapp.com`, and the owner now logs in as `forest@imonsocial.com`. `OWNER_EMAIL` was never updated to match, so `ensure_owner_flag()` has no target.

**Q4 — Production DB binding:** Production's MONGO_URL (resolved server-side) binds to `DB_NAME = imos-admin-test_database`, 174 collections, and it contains the real owner accounts and data. ⚠️ Flag for your awareness: the DB name literally contains the string `test`. It is the DB the live app actually reads/writes (not a stale preview pointer — your real users/data are here), but if that "test" name is not your intended production database name, confirm it independently. It is not the cause of this symptom either way.

## Fix (read-only diagnosis — nothing was changed)
Decide which account is the real owner login (almost certainly `forest@imonsocial.com`, the one used on the iPhone), then in **Deployment Panel → Secrets** set:
- `OWNER_EMAIL` = the exact email of that account (e.g. `forest@imonsocial.com`), and redeploy.

On the next deploy/restart `ensure_owner_flag()` will match that user and set `is_owner:true`; `GET /api/owner/visibility` will then return `is_owner:true` and the Founder Command Center / Request Log / Owner Settings / Billing & Revenue entries will reappear.

(Alternative if you intend to keep `OWNER_EMAIL=forest@imosapp.com`: restore/rename a user's email back to exactly `forest@imosapp.com` — a data change on your side. Setting the secret to the live login email is the simpler path.)
