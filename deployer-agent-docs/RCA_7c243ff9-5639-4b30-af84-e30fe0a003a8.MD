## Verdict
**Not a deploy, secret, key, or crash problem. The owner has hit the daily Live-Jessi voice cap.** The feature is working as designed; the 30-minute/day cap was reached, so `/api/live-voice/session` returns **429** and `/api/live-voice/config` reports `usage.left_s = 0`, which makes the Home "Talk to Jessi / LIVE" button hide itself (it only renders when `left_s > 0`). That reads as "quit working."

## Evidence

### 1. OPENAI_API_KEY present AND valid
- `list_secrets` (active run): `OPENAI_API_KEY` present, `is_empty=false`.
- Proven valid at runtime: user `69be2bc65c4c5af1e821aecc` created **16 Live Jessi sessions today (2026-10-06)**, all `status: closed`, `close_reason: close_requested`, most recent **14:18 UTC (59s)**. A bad/rotated key would surface as `503` + a `WARNING [Live] session create failed 401: ... invalid_api_key`. **None exist** in the last 24h.
- No `503`, `403`, `insufficient_quota`, `model_not_found`, or `rate limit` lines in logs. (I cannot read secret write timestamps, but the key is demonstrably accepted by OpenAI as of 14:18 today, so even if it was rotated it is valid.)

### 2. Logs — only failure is the daily cap
- `GET /api/live-voice/config` → consistently **200** (no 5xx).
- `POST /api/live-voice/session` → **429 Too Many Requests ×2** (at ~21:47 UTC). No other error codes on the live-voice routes.
- Code path (backend/services/live_voice.py `create_session`): checks `configured()` first (→503 if key missing — not hit), then `usage["left_s"] <= 0` → raises `LiveCapReached` → router maps to **429**, *before* OpenAI is ever called. That is exactly the observed 429 with no `[Live]` log line.

### 3. Cap math
- Settings doc `jessi_voice` (last edited 2026-09-19 by forest@imonsocial.com): `daily_cap_min = 30` → **cap_s = 1800**.
- `seconds_today` sums `seconds` for the user's sessions with `started_at >= UTC midnight today`.
- Today's 16 sessions sum to **1814s**: 110+170+197+161+83+84+138+65+54+60+249+134+98+50+102+59.
- Before the 14:18 session the running total was ~1755s (left ~45s, so that session was allowed and ran 59s → 1814s). Every attempt after that is over the 1800s cap → **429 "You have used today's 30 minutes of live Jessi. It resets at midnight."**

### 4. Deploy & pod health
- Latest run 7c243ff9 succeeded 2026-10-06 20:38 UTC and is the active/serving run — not stale or half-applied.
- Pods: 2× Running, `ready=true`, `restart_count=0` → **no crash loop, no startup/import errors.**
- One `Unhealthy` readiness event at 22:04 belonged to a pod being replaced during autoscaling; a fresh pod came up ready at 22:17. Live URL `GET /` → **200** with real app HTML. Earlier `connection refused` lines at 20:39 were just the normal rollout window while the backend booted.

## Why it looks like it "quit a few days ago"
The cap resets at **UTC midnight**, not the owner's local time (`seconds_today` uses `_now().replace(hour=0,...)` in UTC, while the user-facing message says "resets at midnight"). For a US user the window effectively resets early-to-mid evening local, and heavy same-day testing (16 sessions this morning) burns the 30 minutes well before the day feels over — so the button disappears mid-day and reappears "later," which feels intermittent/broken.

## Fixes
1. **Owner (in-app, not Deployment Panel):** This is the owner's own setting. Raise the daily limit in the admin **Voice Lab** (`jessi_voice.daily_cap_min`, max 240), or simply wait for the reset at UTC midnight. Today's usage is 1814s / 1800s — the cap is genuinely exhausted, nothing is broken.
2. **Code / E1 (optional UX, recommended):** On the Home screen, when `usage.left_s <= 0` the button is hidden entirely, which is indistinguishable from "broken." Show an explicit "Daily Jessi voice limit reached — resets at <time>" state instead of hiding the button, and make the reset boundary + copy timezone-aware (currently the cap window is UTC but the message says "midnight"). This removes the "it quit working" confusion. Reproduced the cap logic by reading source in an eph pod; no source bug — purely a UX/clarity improvement.
